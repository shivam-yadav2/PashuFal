# MySQL Persistence Layer — Design

## Intent & why

Champa Dairy & Pashu Kendra (this repo) was generated by AI Studio as a Phase-1
prototype. Its own implementation plan (`.aistudio/artifacts/brain/.../implementation_plan.md`)
states the in-memory store was always a stand-in: *"In-memory seeded
database with mock persistence... Prisma/MySQL schema definition ready for
production DB."* That promise was never kept: `server.ts` imports
`src/server/mockDb.ts`, a singleton holding plain JS arrays that reset on
every restart. `database/schema.sql` (16 tables, FKs, indexes) and
`src/server/db/mysql.ts` (a working connection pool) already exist but are
only exercised by the `/api/health` check.

The owner (Parmeshwar Kushwaha, single farm, no multi-vendor plans) wants
this turned into a real product. First step: make data durable. Second
step (separate plan, follows this one): real server-side auth. Everything
else the owner asked about (admin-editable settings, real photo uploads,
visual design) is explicitly deferred to later phases.

## Goals

- Every domain write (animals, listings, media, contacts, enquiries,
  orders, dairy production/collection, stock movements, subscriptions,
  deliveries, payments, audit log) is persisted in MySQL and survives a
  server restart.
- `server.ts`'s business logic and all existing API routes keep behaving
  exactly as they do today (same status codes, same error messages, same
  JSON shapes) — this is a storage swap, not a feature or API change.
- `src/types/domain.ts` types are unchanged; the frontend is untouched.
- The mock store (`src/server/mockDb.ts`) is deleted, not kept as a
  fallback — the owner was explicit: "use only mysql."
- New repository code has integration tests that run against a real local
  MySQL instance (already installed on the dev machine: MySQL 8.0.44,
  Windows service `MySQL80`).

## Non-goals (this plan)

- Authentication / authorization (next plan).
- Changing the `Animal`/`Contact`/etc. TypeScript shapes.
- Image upload, admin-editable settings, visual redesign.
- Multi-tenant / multi-seller support.
- A migration framework (Flyway/Prisma Migrate) — `database/schema.sql`
  stays the single source of truth, applied by hand via
  `database/init-db.sh`, as today.

## Anti-goals (would make this a failure even if it "works")

- Silent fallback to the mock store when MySQL is unreachable. The app
  must fail loudly on startup if it can't connect — no more "gracefully
  falls back to in-memory" behavior.
- Losing the business-rule parity that's already correct in `mockDb.ts`
  (status-transition guards, idempotent delivery generation, brokerage
  commission handling, audit logging on every mutation). These rules are
  good; they just need to run against real tables.
- Silent precision bugs: MySQL `DECIMAL` columns come back from `mysql2`
  as strings unless configured otherwise. Prices and litre quantities are
  `number` in the domain types; a string leaking through breaks arithmetic
  silently (e.g. `"100" > "99"` is true, `"9" > "80"` is also true).

## Constraints

- MySQL 8.0+ / MariaDB 10.5+ only (matches `schema.sql` header).
- Driver: `mysql2/promise`, already a dependency, already has a working
  pool in `src/server/db/mysql.ts` (`getPool`, `executeQuery`,
  `testMySQLConnection`, `isMySQLEnabled`).
- No ORM introduced — hand-written parameterized SQL, consistent with the
  existing `mysql.ts` style.
- Repository functions must expose the **same method names and signatures**
  as `MockDatabase`'s public API in `mockDb.ts`, so `server.ts` changes to
  a single import line.
- Multi-table writes (animal + listing + media; sale + transaction;
  production/collection entry + its stock movement) must be atomic —
  wrap in a real DB transaction, not sequential independent queries.
- Test runner: none exists today (`package.json` has no `test` script, no
  vitest/jest dependency). This plan adds Vitest (Vite-native, already the
  bundler) and a dedicated test database (`purvanchal_dairy_test` by
  default, overridable via env) that integration tests reset between runs.
- Money math for any derived totals continues to use `multiplyMinor` from
  `src/lib/currency.ts` (existing helper, avoids float drift) rather than
  raw `*`.

## Decisions made (mine, stated so they can be overridden)

1. **File layout**: `src/server/db/repositories/*.ts`, one file per
   domain area (contacts, animals, enquiries, orders, dairy, delivery,
   finance, audit), aggregated by `src/server/db/repositories/index.ts`
   into one `db` object — mirrors the `// --- SECTION ---` groupings
   already in `mockDb.ts`, just split into files.
2. **Seed data**: `database/seed.sql` already matches the schema (unlike
   `mockDb.ts`'s richer fictional dataset, which was written independently
   and never reconciled with the schema). Going forward, `seed.sql` is the
   canonical seed; `mockDb.ts`'s fixture data is not ported over.
3. **Financial summary**: `mockDb.ts.getFinancialSummary()` adds two
   hardcoded offsets (`18450`, `26100`) as fake "opening balances." These
   were arbitrary numbers to make the mock demo look populated. The real
   implementation computes strictly from ledger rows, starting at 0. This
   is a deliberate, visible behavior change, not an oversight.
4. **Date/number deserialization**: configure the pool with
   `dateStrings: true` and `decimalNumbers: true` so MySQL `DATE`/
   `DATETIME`/`TIMESTAMP` columns come back as the ISO-ish strings the
   domain types expect, and `DECIMAL` columns come back as JS `number`,
   matching `Animal.listing.priceMin: number` etc.
5. **Reservation race safety**: `reserveAnimal` must use a conditional
   `UPDATE ... WHERE id = ? AND status = 'AVAILABLE'` (checking
   `affectedRows`) rather than "SELECT then UPDATE," so two concurrent
   reservation attempts can't both succeed.
6. **IDs**: keep the existing human-readable ID schemes (`PDPK-BUF-xxxx`,
   `ENQ-2026-xxx`, `MOV-<timestamp>`, etc.) generated in application code,
   same as `mockDb.ts` — no change to ID shape, since the frontend doesn't
   validate ID format.

## What's left to the builder (the plan)

- Exact SQL for each query/join.
- Exact Vitest setup/teardown mechanics (transaction-per-test vs
  truncate-between-tests).
- Exact row↔domain-object mapping functions.
- Order of task execution within the dependency graph laid out above.
